# ADR-0005: Leaky bucket для rate limiting

- **Статус:** accepted
- **Дата:** 2026-09-21

## Контекст

Нужно ограничить частоту попыток авторизации по трём измерениям:
login (10/мин), password (100/мин), ip (1000/мин).
Возможные алгоритмы: fixed window, sliding window, token bucket,
leaky bucket.

## Рассмотренные варианты

1. **Fixed window.** Просто, но на границе окна пропускает 2× лимита
   (классическая проблема: 10 запросов в конце окна + 10 в начале
   следующего).
2. **Sliding window log.** Точный, но требует хранить timestamp
   каждого запроса — O(N) памяти.
3. **Token bucket.** Хорош для burst-нагрузок, но нам нужно
   ограничение **средней** скорости, а не разрешение всплесков.
4. **Leaky bucket.** Гарантирует равномерный «слив» запросов.
   O(1) памяти, O(1) на операцию, легко тестируется.

## Решение

Выбран **leaky bucket**. Реализация в `internal/limiter/bucket.go`.

Формула: при каждом вызове `Allow()` вычисляем, сколько «воды»
вытекло с прошлого вызова (`elapsed * rate`), вычитаем из `level`.
Если `level + 1 > capacity` — отказ. Иначе `level++`.

## Последствия

- **+** O(1) памяти на ведро.
- **+** Потокобезопасно (`sync.Mutex`).
- **+** Легко покрывается юнит-тестами с виртуальным временем.
- **−** При большом `rate` и малом `capacity` точность падает —
  но у нас другие параметры.
