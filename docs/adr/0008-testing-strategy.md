# ADR-0008: Стратегия тестирования

- **Статус:** accepted
- **Дата:** 2026-09-21

## Контекст

Нужны юнит-тесты на core-логику и интеграционные тесты на API.
ТЗ требует `go test -race -count 100`.

## Решения

### 1. Юнит-тесты — только стандартная библиотека

Не используем `testify`, `gomock`, `mockgen`. Моки пишутся вручную:
структура с полями-функциями, где `nil` = дефолтное поведение.

**Причины:**
- меньше зависимостей;
- явная реализация моков = явное понимание контракта;
- нет магии кодогенерации.

### 2. Интеграционные тесты — через `bufconn`

Не поднимаем реальный TCP-порт. Используем `google.golang.org/grpc/test/bufconn` —
in-memory pipe между клиентом и сервером.

**Причины:**
- на порядок быстрее (нет syscall'ов);
- не занимает порт — можно параллелить;
- не конфликтует с другими тестами в CI.

### 3. `-count 100` только для юнитов

Интеграционные тесты сохраняют состояние (Storage), поэтому `-count 100`
накапливал бы лимиты. В CI используем:
- `go test -race -count 100 ./internal/...` — для юнитов;
- `go test -race -count 1 ./...` — для интеграционных.

### 4. `t.Cleanup` вместо `defer` в параллельных подтестах

`defer cleanup()` в родителе закрывает соединение **до** запуска
параллельных подтестов (`t.Parallel()` откладывает их до конца
родительского теста). Поэтому используем `t.Cleanup(cleanup)` —
он вызывается после всех подтестов.

## Последствия

- **+** Быстрые и стабильные тесты.
- **+** Минимум зависимостей в `go.mod` (`testify` не тянем).
- **−** Больше boilerplate при написании моков.
